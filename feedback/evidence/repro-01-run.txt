6. Summary
======================================================================================
Expected: calling cancelOrder / reduceOrder / reduceOrders on an order id that does not exist should revert with an
order-not-found style error (as amendOrder does: AmendOldOrderGone, and as the pool's own getOrder view does: IncorrectOrder).
Actual: those three functions revert with IncorrectSender(sender, expected) where `expected` is an address that has nothing to do
with the id (3 of 3 gone ids named an unrelated third-party address in this run; the named address changes
over time and per id, and is the zero address for ids that never existed). For order A the true historical owner is 0x9b29D1…c9e7B1,
yet the error names a different address. The same happens through cancelOrderFor for an authorized operator. This reads as an authorization
failure and exposes an unrelated address (the owner check appears to run against whichever order now occupies the id's slot before the
id itself is validated; the later IncorrectOrder check prevents any state change, so this is a clarity/error-semantics issue, not an
exploit). Suggested fix: validate the id first and revert with a dedicated order-not-found error.
